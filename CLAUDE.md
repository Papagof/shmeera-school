# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project status

[SPEC.md](SPEC.md) is the full technical specification for **Shmeera**, a multi-tenant school pickup/drop-off safety app, and remains the source of truth for architecture, data model, API surface, and build order — **read it before starting any implementation work.** Do not re-derive or guess at design decisions that SPEC.md already answers.

The backend (schema, RLS, triggers, 18 Edge Functions including push notification delivery, admin-driven people invites, the offline manual-override release path, and MFA-gated school export/offboarding, a private `shmeera` storage bucket with RLS-scoped student, designee, manual-override, and chat-attachment photos), the admin dashboard (including `/people` for classes/staff/guardians/students — full CRUD, not just add — `/accept-invite` for invited teachers/guardians to set their password, an Alerts page that renders manual-override detail + an acknowledge action, and `/chat` for moderating reported conversations), and both Expo apps (web builds, including the teacher app's class roster tab with photos and its offline-capable manual-override flow, the parent app's designee-request tab with photo capture and designee-aware code generation, and a Chat tab in both apps with realtime delivery and photo attachments) are built and live-verified end-to-end against a real Supabase project — a guardian generating a code, a teacher validating it (manual entry; camera scanning untested outside a simulator), the event showing up in the admin feed, and a push notification firing all work against real infrastructure. The demo seed schools have been deleted from the live project; it's now in active real-world use by an actual admin with real (non-demo) teachers, guardians, and students — see README.md's "Real accounts" section for the original pilot credentials, and "Supabase platform gotchas" below for hard-won fixes already applied — don't reintroduce them.

## What this product is

Three-sided platform (parent/guardian mobile app, teacher/staff mobile app, school admin web dashboard) that verifies who is picking up or dropping off a child via single-use, time-limited, QR/numeric codes, logs every event, and provides moderated 1:1 parent-teacher chat. See SPEC.md §1 for the full product summary.

## Stack (see SPEC.md §2 for the complete table)

- Mobile apps (parent + teacher): React Native + Expo, TypeScript
- Admin dashboard: Next.js (App Router) + TypeScript, on Vercel
- Backend: Supabase — Postgres, Row Level Security, Auth, Realtime, Edge Functions (Deno), Storage
- SMS/OTP/Voice: Twilio (Verify, Programmable SMS, Voice)
- Push: Expo Push Notifications
- Scheduled jobs: Supabase `pg_cron` + Edge Functions

## Non-negotiable architectural rules

These come from SPEC.md §3 (Multi-Tenancy & Tenant Isolation) and must never be relaxed for convenience:

1. **RLS is the security boundary, not application code.** Every table holding school data has a `school_id` column and Row Level Security enabled — no exceptions. Never write a query or Edge Function that relies on app-level filtering alone for tenant isolation.
2. **Never trust a `school_id` from the client.** Every Edge Function resolves the caller's `school_id` server-side from their JWT via the `memberships` table, on the first line of the function, before doing anything else. A `school_id` in a request body may be used for display/filtering only, never for authorization.
3. **No cross-school foreign keys**, enforced with triggers/constraints in addition to RLS (e.g. `guardian_student_links` must have matching `school_id` on both sides).
4. **Per-tenant HMAC secrets** for QR code signing (Supabase Vault) — a code's embedded `school_id` must match the secret used to validate it.
5. **Storage paths are namespaced by `school_id`** (`/schools/{school_id}/...`) with matching storage RLS policies.
6. **Realtime channels are named `school:{school_id}:...`** and must be backed by RLS so a user cannot subscribe outside their own school, even by guessing a channel name.
7. **Chat is strictly 1:1** (one guardian, one teacher, one student context) — never group chat. Enforce via RLS joins through `guardian_student_links` + `classes.teacher_id`, not UI hiding.
8. **Every isolation change needs a regression test.** When adding or modifying a table, Edge Function, or RLS policy, add/update the cross-tenant isolation test (seed two fake schools, assert zero cross-tenant reads) per SPEC.md §3.3.9 before considering the change done.
9. **Mandatory geolocation at scan-time** (SPEC.md §6.7) is a required control on `validate-event-code`, not an optional enhancement — do not make it silently skippable.
10. **Designees must be admin-approved** before a code can be generated for them — this check belongs in `generate-event-code`, server-side, never client-trusted.

## Supabase platform gotchas (found via live testing, don't reintroduce)

1. **`vault` schema is never reachable via `.schema("vault")` from supabase-js**, even for `service_role` — PostgREST's Data API only exposes `public`/`graphql_public`. Every Vault read/write from an Edge Function must go through a `SECURITY DEFINER` wrapper function living in `public` (see `public.vault_get_decrypted_secret` / `public.vault_create_secret`, migration `20260902100011_vault_rpc.sql`), called via `.rpc(...)`. Calling `.schema("vault").from(...)` or `.schema("vault").rpc(...)` directly fails with an opaque error, not a helpful one.
2. **Custom schemas need explicit grants for `service_role`, not just `authenticated`.** Every Edge Function writes through the service-role client, and any trigger that calls a helper function in a non-`public` schema (e.g. `private.assert_same_school`) runs with the *invoking* role's privileges (`SECURITY INVOKER` by default) — so `service_role` needs its own `GRANT USAGE ON SCHEMA ... TO service_role` and `GRANT EXECUTE ... TO service_role`, granting to `authenticated` alone is not enough and fails with "permission denied for schema X" only when the write comes from an Edge Function, not from direct SQL.
3. **Don't check `current_setting('request.jwt.claim.role', true) = 'service_role'` in triggers.** This PostgREST project doesn't reliably populate that flattened per-key GUC; use Supabase's built-in `auth.role() = 'service_role'` instead (it checks the flattened GUC and falls back to parsing the JSON `request.jwt.claims`).
4. When an Edge Function throws a generic `HttpError` wrapping a Postgres error, the real `error.message/details/hint/code` gets silently dropped (`errorResponse` only logs on the non-`HttpError` catch-all path). When debugging a mysterious 4xx/5xx from a deployed function, temporarily log the underlying error before wrapping it, redeploy, reproduce, then revert — don't guess from the generic message alone.
5. **`supabase-js`'s `functions.invoke()` never surfaces the real error body.** A non-2xx response from any Edge Function here (all of which return `{ "error": "..." }`, see `supabase/functions/_shared/errors.ts`) only ever produces the generic client-side message "Edge Function returned a non-2xx status code" — the actual reason is on `error.context` (a raw `Response`) and has to be parsed out manually. Every screen calling `invoke()` uses `describeFunctionError` from `@shmeera/shared` (`packages/shared/src/functionError.ts`) instead of `error.message` directly — use it for any new call site too, especially ones whose specific failure reason matters (e.g. the teacher app's STOP screen).
6. **`guardian_student_links` RLS is scoped by `student_id`, not `guardian_id`.** `gsl_select` (SPEC.md §7) grants access to any link row whose `student_id` is one of the caller's own linked/taught students — which is correct for a teacher (sees every guardian of their own students) but means a guardian querying `guardian_student_links` unfiltered gets back *every* guardian's link row for any child they share (e.g. another parent, or an emergency contact), not just their own. Found live when a two-guardian child rendered twice in the parent app's children list. Any query against this table for "my own relationships" must filter explicitly by the caller's own `guardian_id` (see `ChildListScreen`'s `load()`, which first resolves the caller's own `guardians.id` via `user_id = auth.uid()`, then filters on it) — don't rely on RLS alone to scope it to "rows I own."
7. **Direct (non-service-role) inserts into `classes`/`students`/`guardian_student_links` from the admin dashboard must include `school_id` explicitly.** The client only has an anon/authenticated session, not service_role, so `school_id` isn't implied by anything — omitting it produces a generic RLS 403 ("new row violates row-level security policy"), not a helpful "school_id is required" error, because the `with check` clause evaluates false against a null `school_id` before any not-null constraint is reached. Resolve the admin's own `school_id` server-side (from `memberships`, see `apps/admin/src/app/(dashboard)/people/page.tsx`) and pass it into every insert.
8. **`new Date(...).toLocaleTimeString()` (or any locale/timezone-dependent formatting) in a Server Component's props chain causes a Next.js hydration mismatch** when the server process's default locale/timezone differs from the viewer's browser (found live: server rendered "17:48:32", browser rendered "5:48:32 PM"). This is expected — the server can't know the viewer's timezone — so the fix is `suppressHydrationWarning` on that specific node (React's documented escape hatch for intentionally-client-varying values, see `live-events-feed.tsx`), not a restructure to make server and client agree.
9. **A Supabase invite/recovery email link hands off a session via a URL hash fragment (`#access_token=...&refresh_token=...`), not a query param or cookie** — fragments are never sent to the server, so (a) any middleware/proxy that gate-keeps unauthenticated requests must explicitly allow-list the landing page (`isPublicPath` in `proxy.ts` must include `/accept-invite`, the same way it includes `/login`) or the server-side redirect fires before the page's client JS ever runs and parses the hash; and (b) the landing page itself must parse `window.location.hash` and call `supabase.auth.setSession({access_token, refresh_token})` explicitly — `@supabase/ssr`'s cookie-backed browser client does not auto-detect a session from the hash the way a plain localStorage-backed client would. All three of these (missing `redirectTo` on `inviteUserByEmail`, no accept-invite page at all, and the proxy not allow-listing it) were live bugs found from a real user actually clicking a real invite email — see `apps/admin/src/app/accept-invite/page.tsx` and `apps/admin/src/proxy.ts`.
10. **`inviteUserByEmail` errors "already registered" if called twice for the same email**, even if the person never completed the invite (no password set) — there is no built-in "resend." Use `supabase.auth.resetPasswordForEmail(email, { redirectTo })` instead (the public/anon `/auth/v1/recover` REST endpoint) to get them a fresh working link; it produces the same hash-fragment handoff and lands on the same `/accept-invite` page, so no separate code path is needed.
11. **The default Supabase-hosted email sender is dev-only and aggressively rate-limited** (`over_email_send_rate_limit`, roughly a handful of sends per hour) — expect to hit this while testing invites/resets in a single session. It's a rolling-window throttle, not a hard cap; retrying after it clears works. Configure a real SMTP provider (Authentication → Emails → SMTP Settings in the dashboard — no MCP tool manages this) before inviting real people at any volume.
12. **An "offline" code path must never resolve anything it needs via a live network call**, even a read from a table RLS already lets the caller see. The manual-override flow originally resolved `school_id` via `supabase.from("memberships").select(...)` inside its submit handler — reasonable-looking, but that query itself requires network, so on a genuinely offline device the whole flow failed with an error instead of ever reaching the local-queue fallback (found live by actually cutting network mid-flow with Playwright's `context.setOffline(true)`, not by inspection). Fixed by caching `school_id` locally (`rosterCache.ts`) during the last successful online fetch, same as the roster itself — audit every "works offline" code path for this exact mistake, not just the obviously-network-shaped parts.
13. **`expo-camera`'s `takePictureAsync({ base64: true })` returns a full `data:image/jpeg;base64,...` data URL on web**, but a bare base64 string on native — `atob()` throws on the former. Strip a `data:image\/\w+;base64,` prefix once, immediately after capture, rather than at every later use site (found live: `atob` threw "The string to be decoded is not correctly encoded" on submit).
14. **Switching a tab `Pressable` to the tab that's already active does not remount that screen** (React doesn't re-run effects when the conditionally-rendered component instance doesn't change) — so any "retry on mount" logic (e.g. flushing a locally-queued item once back online) silently never fires if the user just stays on that screen instead of navigating away and back. Found live: a manual override queued while offline never synced despite the network coming back, because the roster screen was already the active tab. Don't rely on navigation timing for a "back online" retry — pair it with an explicit interval poll and/or a manual retry action (see `RosterScreen`'s 20s poll + "Sync now" button).
15. **A `memberships` row's `school_id` is schema-required (not-null) even for `super_admin`, whose role is conceptually platform-wide, not school-scoped.** Any code that deletes a user's auth identity based on "no memberships left after this school's rows are removed" must explicitly exclude `super_admin` memberships from that check — otherwise offboarding the one school a super_admin's membership row happens to reference silently deletes that platform operator's own account. Found before it shipped, by deliberately testing offboarding against a super_admin whose only membership was in the school being deleted (see `offboard-school`).
16. **`audit_log`'s FK to `schools` originally cascaded**, which would have deleted the audit trail *of the offboarding itself* the moment `offboard-school` deleted the school row — exactly backwards for a table whose entire purpose is surviving the events it records. Fixed by dropping the cascade (`20260902100019_school_offboarding_support.sql`); `school_id` keeps its historical value as a plain (non-FK-enforced) column after the school is gone. Any future table meant to be an immutable audit/history record needs the same treatment — a cascading FK to the entity it's logging is a design smell, not a convenience.
17. **`auth.users` has a `no action` (restrict) FK from `audit_log.actor_id`**, not cascade — a user who has ever acted (including via `service_role`) cannot be hard-deleted while their audit rows exist, full stop, not even via `service_role`. This is correct and desirable (accountability survives account deletion) but means "hard delete this test/throwaway user" can fail with a FK violation once they've done anything audited — don't work around it by deleting their audit rows; leave the account orphaned instead, exactly as `offboard-school` does for a super_admin caller.
18. **`sweep-expired-codes` and `purge-retention` are deployed with `verify_jwt: false`** (required — `pg_cron`'s `net.http_post` call carries no Supabase user session to verify), which means `CRON_SECRET` is not a defense-in-depth nicety for these two functions, it's the *only* thing standing between them and being fully public, unauthenticated endpoints anyone on the internet could POST to. Found live: both had been deployed and were reachable with `CRON_SECRET` unset — the code's `if (CRON_SECRET && ...)` fallback (intended so local dev doesn't need every secret configured) meant the check silently never ran at all. Set `CRON_SECRET` before relying on either function; never commit its real value to a migration file (see `20260902100021_enable_pg_net_and_schedule_cron_jobs.sql`, which keeps a placeholder — the live `cron.job` rows have the real value, applied directly and not tracked in git).
19. **`deploy_edge_function`'s `verify_jwt` parameter defaults to `true` and is not "sticky" across redeploys** — omitting it on a redeploy silently resets a function that was intentionally deployed with `verify_jwt: false` (e.g. for `pg_cron`, which has no Supabase session to attach) back to `true`. This is exactly what happened redeploying `sweep-expired-codes` for an unrelated Twilio change: the platform-level JWT gate started rejecting every `pg_cron` call with `"Missing authorization header"` — a completely different failure from the function's own `CRON_SECRET` check, and easy to misdiagnose as a secret-value mismatch instead (which is what happened here first). Always pass `verify_jwt` explicitly on every redeploy of a function that isn't meant to require one, and check `list_edge_functions` after any redeploy of a `verify_jwt: false` function to confirm it's still `false`.
20. **When a "wrong value" theory survives one re-paste but not two, stop trusting the theory and get a byte-level diagnostic instead of asking for a third re-paste.** A trailing newline from a copy/paste (e.g. copying a whole line from an editor instead of just the token) is invisible in every normal comparison and log line, but shows up immediately as a length mismatch — `CRON_SECRET`'s stored value was 44 chars against an expected 43, the extra byte being `\n`. A temporary endpoint branch that echoes back lengths and a few characters from each end (never the full value) is safe to ship for one redeploy-diagnose-revert cycle and finds this class of bug in one round trip instead of several blind guesses.
21. **A working Edge Function + a working admin review UI does not mean a feature is actually usable end to end.** Found repeatedly this session: chat had `send-chat-message`/`get-chat-thread`/`report-chat` fully deployed and tested, but zero UI in either mobile app; `generate-event-code` fully supported `designee_id`, but `ChildListScreen` never sent one, so a designee code could never actually be generated even after admin approval; `events`/`designees` already carried a `photo_url` field the teacher's `ResultScreen` and admin's `DesigneeQueue` both received, but neither ever rendered it. Backend-complete is not feature-complete — when asked to "finish" or "wire up" a feature, grep every screen in every app for the relevant table/function name before assuming the UI already uses what the backend provides.
22. **Deploying `apps/admin` to Vercel from an npm-workspaces monorepo via a root-level `vercel.json` with a custom `buildCommand`/`installCommand`/`outputDirectory` override reliably fails at the "Deploying outputs" step** with `"Cannot patch preview comments when immutable static file upload is enabled. Upgrade to next@v16.3.0-canary.32 or newer to resolve this."` — even though the build itself succeeds (all routes compile/typecheck cleanly). This happens on both CLI-triggered and git-triggered deploys, so it isn't a CLI-vs-git-integration issue. Fix: don't use a custom `vercel.json` at all — set the project's **native** Root Directory and Framework Preset instead (`vercel project update <project> --root-directory apps/admin --framework nextjs`), which lets Vercel use its own monorepo-aware build path. Confirmed live: identical commit, only the deploy-config mechanism changed, and the error stopped recurring.
23. **`apps/parent` and `apps/teacher` (Expo, no `expo-router`) deploy to Vercel the same way as `apps/admin`** — native Root Directory (`apps/parent` / `apps/teacher`), `--framework other` (Expo isn't a Vercel-recognized preset), `--build-command "npx expo export -p web"`, `--output-directory dist`. No SPA rewrite is needed since there's no client-side routing. Each app's `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` must be added as Vercel project env vars (`vercel env add ... --project <name>`) — the local `.env` files are gitignored and the build never sees them otherwise.
24. **The repo has one root-level `.vercel/project.json` linking the CLI's ambient context to a single Vercel project at a time** — `vercel deploy`/`vercel env add` without `--project` (or without `--cwd` pointing elsewhere) silently act on whichever project that file currently names. Deploying `shmeera-parent` right after working on `shmeera-admin` without switching it first added an env var to the wrong project on the first attempt (caught immediately from the command's own "Project godfrey5/shmeera-admin" confirmation line, then removed). `vercel env add` supports `--project <name>` directly (no relink needed) but `vercel deploy` does not — for that one, overwrite `.vercel/project.json`'s `projectId`/`projectName` with the target project, deploy, then restore it back to whichever project should stay the ambient default (here, `shmeera-admin`) when done.

## Working conventions

- Treat SPEC.md's data model (§7) and Edge Function list (§8) as authoritative names/shapes for new tables and functions unless the user explicitly asks to change the design — if a change is needed, update SPEC.md alongside the code so the spec stays in sync.
- Follow the build order in SPEC.md §10 when sequencing new work, particularly: **write the RLS isolation test suite before building UI on top of new tables.**
- This is a safety-critical child-release system — prioritize correctness and auditability (immutable `audit_log` rows, insert-only) over speed of iteration.
