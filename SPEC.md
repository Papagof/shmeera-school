# Shmeera School — School Pickup & Drop-off Safety App
### Full Technical Specification & Build Prompt (Multi-Tenant + In-App Chat)

Use this document as a build prompt for an AI coding assistant (Claude Code, Cursor, etc.) or as a spec for a development team.

---

## 1. Product Summary

**Shmeera** is a multi-tenant, three-sided safety platform that verifies the identity of whoever is dropping off or picking up a child at school, in real time, keeps school administration informed of every event, and gives parents and teachers a secure, moderated channel to communicate — all while guaranteeing that **no school can ever see, query, or leak another school's data.**

**Roles:**
1. **Parent/Guardian (React Native app)** — generates a time-limited, single-use pickup/drop-off code (numeric code + QR) for themselves or an authorized designee; chats with their child's teacher.
2. **Teacher/Staff (React Native app, or web on a school tablet)** — scans the QR code or manually enters the token to verify and log the event; chats with parents of students in their class.
3. **School Admin (Next.js web dashboard on Vercel)** — sees a live feed of all events, gets alerted on anomalies, manages guardians/students/staff, can broadcast emergency notices, and can moderate/audit all chat activity within their school only.

**Core safety guarantee:** a child is only released to a person holding a valid, unexpired, single-use code tied to that specific child, generated by a verified guardian account, with the event immediately logged and broadcast to admin. Every school operates in a fully isolated tenant — one compromised or malicious school account can never reach another school's students, guardians, staff, or messages.

## 3. Multi-Tenancy & Tenant Isolation Architecture

This is the section that guarantees "different schools can use the app independently without any security breach." Treat every rule below as non-negotiable.

### 3.1 Isolation model
- **Shared database, tenant-scoped by `school_id`, enforced at the database layer — not the application layer.** Every table that holds school data carries a `school_id` column, and **every single one has Row Level Security enabled with no exceptions.**
- Application code (mobile apps, Edge Functions, dashboard) is **never trusted** to filter by `school_id` correctly. RLS policies are the actual security boundary; app-level filtering is only a UX convenience layered on top.
- `auth.users` is shared across tenants (one login system), but a **`memberships` table** maps each `user_id` → `school_id` + `role`, and every RLS policy joins through `memberships` to resolve "which school(s) can this user see," never trusting a `school_id` sent by the client.
- **Billing/tenant unit is the individual school** — the product is sold per-school, each school is its own billing entity, and `school_id` is the top-level tenant boundary. There is no `district_id` layer above it; a district wanting multiple schools on the platform simply holds multiple independent school subscriptions rather than one umbrella account.

### 3.2 Standard RLS pattern (applied to every tenant table)
```sql
alter table students enable row level security;

create policy "tenant_isolation_select"
on students for select
using (
  school_id in (
    select school_id from memberships where user_id = auth.uid()
  )
);
-- Equivalent policies for insert/update/delete, further narrowed by role
-- (e.g. guardians only see rows reachable via guardian_student_links).
```
This pattern is applied uniformly to `students`, `guardians`, `staff`, `classes`, `event_codes`, `events`, `security_alerts`, `audit_log`, `chat_threads`, `chat_messages`, `designees` — no table is exempt.

### 3.3 Additional isolation safeguards
1. **No cross-school foreign keys.** A guardian in School A can never be linked (`guardian_student_links`) to a student in School B — enforced with a Postgres trigger/check constraint that verifies both rows share the same `school_id`, not just relying on RLS.
2. **Per-tenant secrets for QR signing.** Each school gets its own HMAC signing secret (stored in Supabase Vault) for `event_codes.qr_payload`. A leaked or forged code from School A's format cannot validate against School B, even if someone tried to replay it — the validation Edge Function looks up the secret by the code's embedded `school_id` and rejects any mismatch.
3. **Storage isolation.** Supabase Storage buckets are namespaced by `school_id` in the path (`/schools/{school_id}/students/{student_id}/photo.jpg`) with storage RLS policies mirroring the database policies — a signed URL for one school's photo can't be swapped to fetch another's.
4. **Edge Function tenant guard.** Every Edge Function resolves the caller's `school_id` server-side from their JWT/`memberships` row on the **first line of the function** — never accepts a `school_id` parameter from the request body for authorization decisions (it may be used for pure display/filtering only, and is always cross-checked).
5. **Realtime channel scoping.** Supabase Realtime channels (for both the live admin event feed and chat) are named `school:{school_id}:...` and Realtime Authorization (RLS on the underlying tables that back the channel) prevents a user from subscribing to a channel outside their own `school_id`, even if they know/guess the channel name.
6. **Admin scoping.** `school_admin` role is scoped to exactly one `school_id` via `memberships`. A separate, more tightly controlled `super_admin` role (platform operator only, MFA-required, all actions logged) is the only role that can act across schools, and even then only through dedicated, heavily audited platform-support tooling — never through the regular app APIs.
7. **Per-tenant rate limiting** on code generation, validation attempts, and chat messages, keyed by `school_id` + `user_id`, so abuse in one school can't degrade service for others (shared infrastructure, isolated blast radius).
8. **Tenant-level audit trail.** Every `audit_log` row is `school_id`-scoped and immutable (insert-only, no update/delete policy granted to any app role); `school_admin` can only ever query their own school's audit log.
9. **Automated isolation testing.** CI includes RLS regression tests: seed two fake schools, assert that every role in School A gets zero rows when querying School B's data across every table and every Edge Function — this test suite blocks merges if it fails.
10. **School onboarding/offboarding** is its own controlled flow (super_admin only): creates the `schools` row, generates the per-tenant signing secret, provisions the initial `school_admin` membership, and — on offboarding — supports full tenant data export followed by hard deletion, not just a "soft disable" flag.

## 4. User Roles & Permissions (Supabase RLS model)

- `super_admin` — platform operator; onboards/offboards schools; cannot read student/guardian/chat data through normal app paths, only through audited support tooling.
- `school_admin` — full read on **their** school's data only (enforced per §3); manages staff, guardians, students; views all logs; issues emergency broadcasts; revokes codes; can view/moderate chat threads within their school for safety review.
- `teacher` — sees only their assigned class roster; validates codes; chats only with guardians of students in their own class(es); cannot see other classes, other teachers' threads, or guardian phone numbers beyond what's needed to confirm identity.
- `guardian` — sees/manages only their own linked children; generates codes only for children they're linked to; chats only with the teacher(s) of their own child's class.

All access is enforced with Postgres Row Level Security tied to `auth.uid()` via `memberships`, never trusted from the client alone.

## 5. Core User Flows

### 5.1 Guardian generates a pickup/drop-off code
1. Parent opens app, selects child (if multiple), selects **Drop-off** or **Pickup**.
2. App calls Edge Function `generate-event-code`.
3. Function resolves the caller's `school_id` from their membership (never from the request), then verifies: caller is an active, verified guardian of that child within that school; child's school-day status allows this action; no existing unexpired code for this child+type.
4. Function creates a row in `event_codes`: 6-digit numeric code + QR payload HMAC-signed with that school's per-tenant secret, `expires_at` = now + 10 minutes (configurable per school), `single_use = true`.
5. Code + QR rendered on parent's screen; optionally also sent via Twilio SMS as a backup if the phone is handed to a driver/nanny.
6. For a designated pickup person (grandparent, babysitter), the parent first submits a **Designee Request** (name, phone, relationship, optional photo). The designee is in `pending` status and **cannot be used to generate a code yet**. School admin reviews and approves (or rejects) the request from the dashboard; only once `status = 'approved'` can the guardian generate a **Designee Code** for that person. The designee gets an SMS with the code via Twilio, and their name/photo is shown to the teacher at scan time.

### 5.2 Teacher validates at the gate
1. Teacher opens Teacher app, taps **Scan Code**.
2. Scans QR (or types the 6-digit code if QR fails).
3. Teacher app attaches the device's current location to the request (mandatory — see §6.7). Edge Function `validate-event-code` resolves the school from the teacher's membership, verifies the code's embedded `school_id` matches, checks it's not expired/used, matches the child assigned to that teacher/class, requires a location payload to be present, and (if a designee code) displays the designee's name/photo.
4. Teacher confirms with a single tap ("Confirm release of [Child] to [Name]").
5. Code is marked `used_at`; event written to `events`; push/SMS notification fires to the guardian (confirmation) and the school admin dashboard (realtime feed) — all scoped to that school's Realtime channel.
6. If invalid/expired/reused/wrong-tenant, the teacher app shows a hard red **STOP** screen and logs a `security_alert` that immediately pings that school's admin.

### 5.3 School admin oversight
- Live dashboard (Supabase Realtime, subscribed only to their `school:{school_id}` channel) of all check-ins/check-outs, filterable by class/grade.
- Automated alerts for security alerts, late pickups, repeated failed validations, and custody-restricted attempts (see §6).
- Admin can revoke any active code, freeze a guardian account, or issue a school-wide emergency broadcast — always scoped to their own school only.

### 5.4 Parent–Teacher Chat
1. Chat is **strictly 1:1** — every thread has exactly one guardian and exactly one teacher, never a group. A chat thread is auto-created the first time a guardian is linked to a student (`guardian_student_links` insert trigger creates a `chat_threads` row scoped to that one guardian + the student's assigned primary teacher, tagged with `school_id`). If a student has multiple guardians, each guardian gets their own separate 1:1 thread with the teacher — guardians never see each other's messages. If a class has co-teachers, the thread is tied to the student's single assigned primary teacher, not all of them.
2. Both parties see the thread in-app; messages sync via Supabase Realtime (Postgres changefeed on `chat_messages`, filtered by RLS so only the two participants and their `school_admin` can read it).
3. **Guardrails:**
   - Chat is **scoped to one student's context** — a guardian cannot message a teacher who isn't tied to one of their linked children, and a teacher cannot message a guardian outside their own class roster. Enforced via RLS join through `guardian_student_links` + `classes.teacher_id`, not just UI hiding.
   - **School-hours / quiet-hours setting** (admin-configurable): messages sent outside school hours are queued and delivered with a "sent outside school hours" label rather than pushed immediately, reducing after-hours pressure on teachers (still visible in-thread).
   - **No cross-tenant leakage:** `chat_threads` and `chat_messages` carry `school_id` and inherit the same tenant-isolation RLS pattern from §3.2; realtime channel is `school:{school_id}:thread:{thread_id}`.
   - **Admin visibility is always-on, not report-gated:** `school_admin` can open any thread within their school at any time (not restricted to only after a report is filed) — this is a deliberate choice for safety oversight. Every such read is logged in `audit_log` whenever an admin views a thread they're not a participant in, and schools disclose this policy to parents/teachers at onboarding so the always-on access is transparent, not silent surveillance.
   - **Attachments** (photos, documents) go through Supabase Storage with the same per-school namespacing and virus/type scanning via an Edge Function before the message is marked delivered.
   - **Reporting/blocking:** either party can flag a message or thread, which creates a `security_alert`-style `chat_report` visible to admin; admin can mute a thread or account pending review.
   - **Retention:** chat messages follow the same school-configurable retention/purge policy as event logs (§7.10 → now §8.10).
   - **Push notifications** for new messages via Expo Push, with Twilio SMS fallback only for urgent/flagged messages (not for ordinary chat volume, to avoid SMS cost/spam).

## 6. Safety & Trust Measures

1. **Verified guardian onboarding** — guardians are added by school admin or self-register and are approved by admin before being linked to a child.
2. **Phone number verification via Twilio Verify** at signup and whenever a guardian's phone number changes.
3. **Single-use, short-lived codes** (default 10 min TTL, independently configurable per school via `schools.settings`).
4. **Cryptographically signed, per-tenant QR payloads** (HMAC signed server-side with a per-school secret, see §3.3.2).
5. **Custody restriction flags** — block + immediately escalate any code generation/validation attempt involving a restricted guardian.
6. **Admin-approved designees only** — a guardian cannot generate a code for anyone who isn't a pre-approved designee; every designee is submitted by the guardian and must be reviewed and approved by school admin before it can be used, closing off a path where a parent could hand pickup rights to an unvetted person on the fly. **Designee photo requirement** (optional, school-configurable) adds visual confirmation at the gate on top of this.
7. **Mandatory geolocation capture at scan-time** — the teacher app requires device location permission and a fresh location fix before `validate-event-code` will submit; if location can't be obtained (permission denied, GPS unavailable), the release cannot be confirmed through the normal flow and falls back to the offline manual-override path (§6.13), which is itself flagged for admin review. This is a required control, not opt-in, so every release event has a verifiable location on record.
8. **Full immutable, tenant-scoped audit log** covering code events, validations, revocations, failed attempts, and admin access to chat threads.
9. **Late-pickup escalation ladder** — default e.g., 15 min: notify guardian; 30 min: notify admin; 45 min: admin gets a Twilio Voice call — with each school independently able to set its own thresholds and steps via `schools.settings` (a district running multiple schools is not forced into one shared timing policy).
10. **Rate limiting & anomaly detection**, keyed per-tenant, on code generation, validation attempts, and chat messages.
11. **Data minimization & retention policy** — event logs and chat auto-purge per a school-configured retention window; photos/PII/location data encrypted at rest with short-lived signed URLs.
12. **Compliance posture** — designed with COPPA/FERPA principles (or local equivalent) in mind; parental and staff consent to mandatory location capture obtained at onboarding; data processing agreement template per school; chat monitoring policy disclosed to users.
13. **Offline fallback** — teacher app caches the last-synced roster and allows manual override with mandatory photo + note if connectivity or location drops, flagged for admin review on resync.
14. **Two-person confirmation for unusual releases** (school-configurable).
14. **Automated cross-tenant isolation testing** in CI (see §3.3.9) as a standing safety measure, not a one-time check.

## 7. Data Model (Supabase / Postgres — simplified)

```sql
schools (id, name, timezone, settings jsonb, signing_secret_ref text, created_at)
        -- settings jsonb holds per-school configuration decided independently
        -- by each school's admin, e.g.:
        --   { "code_ttl_minutes": 10,
        --     "escalation_ladder": [
        --       { "after_minutes": 15, "action": "notify_guardian" },
        --       { "after_minutes": 30, "action": "notify_admin" },
        --       { "after_minutes": 45, "action": "voice_call_admin" }
        --     ],
        --     "designee_photo_required": false,
        --     "retention_days": 365 }

memberships (id, user_id references auth.users, school_id references schools,
             role text check (role in ('super_admin','school_admin','teacher','guardian')),
             created_at)

staff (id, school_id, user_id references auth.users, class_id, phone, created_at)

classes (id, school_id, name, teacher_id)

guardians (id, school_id, user_id references auth.users, full_name, phone,
           phone_verified boolean, status text, created_at)

students (id, school_id, class_id, full_name, dob, photo_url, status text, created_at)

guardian_student_links (id, school_id, guardian_id, student_id, relationship,
                         is_primary boolean, pickup_authorized boolean, restriction_note text)
                         -- trigger enforces guardian.school_id = student.school_id = school_id

designees (id, school_id, requested_by_guardian_id, student_id, full_name, phone,
           relationship, photo_url, status text check (status in ('pending','approved','rejected')),
           reviewed_by uuid null, reviewed_at timestamptz null, expires_at)
           -- event_codes.designee_id may only reference a row where status = 'approved'
           -- (enforced by the generate-event-code Edge Function, not client-trusted)

event_codes (id, school_id, student_id, type text check (type in ('dropoff','pickup')),
             code text, qr_payload text, issued_by uuid, designee_id uuid null,
             expires_at timestamptz, used_at timestamptz null, revoked boolean, created_at)

events (id, school_id, student_id, event_code_id, type, validated_by_staff_id,
        released_to_name text, geo jsonb not null, device_info jsonb, created_at)
        -- geo capture is mandatory at scan-time (see §6.7 Mandatory geolocation
        -- capture); validate-event-code rejects the request if the teacher
        -- device does not supply a fresh location fix

security_alerts (id, school_id, student_id null, kind text, details jsonb,
                  acknowledged_by uuid null, created_at)

chat_threads (id, school_id, student_id, guardian_id, teacher_id, status text,
              muted boolean default false, created_at)
              -- strictly 1:1: unique constraint on (guardian_id, teacher_id, student_id)
              -- guarantees exactly one guardian and one teacher per thread, no group chats

chat_messages (id, school_id, thread_id, sender_id, sender_role, body text,
               attachment_url text null, delivered_after_hours boolean default false,
               created_at)

chat_reports (id, school_id, thread_id, message_id null, reported_by uuid,
              reason text, status text, created_at)

audit_log (id, school_id, actor_id, actor_role, action, target_table, target_id,
           metadata jsonb, created_at)
```

Every table above carries `school_id` and has RLS enabled per the pattern in §3.2, with `chat_threads`/`chat_messages` additionally scoped to their two participants (+ admin, logged) via join.

## 8. API / Edge Functions

- `POST /functions/v1/request-designee` — guardian-only, creates a `designees` row with `status = 'pending'`, notifies admin.
- `POST /functions/v1/review-designee` — admin-only, approves or rejects a pending designee request, notifies the requesting guardian.
- `POST /functions/v1/generate-event-code` — guardian-only, tenant-resolved server-side, returns code + signed QR payload; for designee codes, rejects the request server-side unless the designee's `status = 'approved'`.
- `POST /functions/v1/validate-event-code` — staff-only, validates tenant + code match, logs event, fires notifications.
- `POST /functions/v1/revoke-code` — admin/guardian, invalidates an active code.
- `POST /functions/v1/emergency-broadcast` — admin-only, fans out push + Twilio SMS within their own school only.
- `POST /functions/v1/send-chat-message` — validates thread participancy + tenant match, applies quiet-hours logic, writes message, triggers push.
- `POST /functions/v1/get-chat-thread` — returns a thread + its messages; routes admin reads through a server-side check so a read by an admin who isn't a participant can be logged to `audit_log` (Postgres has no SELECT trigger to hook this at the DB layer — see §5.4.3). Participants may also read their own thread directly via RLS.
- `POST /functions/v1/report-chat` — creates a `chat_reports` row, notifies admin.
- `POST /functions/v1/twilio-webhook` — inbound Twilio status callbacks (delivery receipts, verify results).
- `POST /functions/v1/onboard-school` — super_admin only, MFA-gated, creates a new tenant + signing secret + initial admin membership.
- `POST /functions/v1/invite-member` — school_admin only, tenant-resolved server-side; invites a teacher or guardian by email (Supabase Auth invite — they set their own password) and links them into the admin's own school via `memberships` + `staff`/`guardians`. Re-inviting an email that's already registered links the existing auth user instead of erroring.
- `POST /functions/v1/register-push-token` — authenticated, upserts the caller's Expo push token for delivery of the notifications in §9.
- Scheduled function `sweep-expired-codes` (pg_cron, every minute) — marks expired codes per each school's own `code_ttl_minutes`, and triggers that school's own escalation ladder from `schools.settings`.
- Scheduled function `purge-retention` (pg_cron, daily) — purges events/chat past each school's configured retention window.

## 9. Notifications Matrix

| Event | Guardian | Teacher | Admin |
|---|---|---|---|
| Designee request submitted | in-app confirmation | — | push + dashboard alert |
| Designee request approved/rejected | push + in-app | — | in-app confirmation |
| Code generated | in-app confirmation | — | — |
| Code validated (successful release) | push + SMS | in-app | realtime dashboard |
| Invalid/expired/reused/wrong-tenant code attempt | push alert | red-screen block | push + SMS + dashboard alert |
| Custody-restricted guardian attempt | — | red-screen block | push + SMS + phone call escalation |
| Late pickup (per ladder) | push → SMS | — | push → SMS → voice call |
| Emergency broadcast | push + SMS | push + SMS | — |
| New chat message | push (SMS only if flagged urgent) | push (SMS only if flagged urgent) | — |
| Chat report filed | — | — | push + dashboard alert |

## 10. Suggested Build Order (MVP → v1)

1. Supabase project: schema, `memberships`-driven RLS on every table, per-tenant signing secrets, Auth (email + phone).
2. **RLS isolation test suite first** — seed two fake schools, assert zero cross-tenant reads before building any UI on top.
3. Twilio: Verify service for phone verification; Messaging + Voice services for alerts.
4. Parent RN app: auth, child list, code generation + QR display, event history, chat with teacher.
5. Teacher RN app: auth, class roster, QR/code scan, validate flow, offline cache, chat with guardians.
6. Admin Next.js dashboard on Vercel: live events feed (Realtime, tenant-scoped), guardian/student/staff management, designee approval queue, alert center, emergency broadcast, chat moderation/reports view.
7. Edge Functions: code generation, validation, revoke, broadcast, designee request/review, chat send/report, school onboarding, expiry sweep, retention purge.
8. Notification wiring: Expo Push + Twilio SMS/Voice.
9. Security hardening pass: rate limiting, HMAC signing, audit log review, RLS penetration test, storage bucket namespacing check.
10. Pilot with one school → validate isolation guarantees hold under real load → onboard a second school and re-run the cross-tenant test suite against live data → iterate.
